* For vault-wide canonicalization or dedupe passes, make a backup archive of `~/my-data` first before broad edits. If using Claude Code for the cleanup, expect that a full-vault pass may need multiple runs or `--continue` because the first pass can hit max-turn limits or get interrupted. After Claude finishes, do a manual verification pass on the changed notes and search for leftover anti-patterns like `Recent Interactions`, `Reasoning`, or duplicated operational details still sitting in people/entity notes.
* When doing cross-note dedupe cleanups (especially with a coding agent like Claude Code), do not stop after the first pass. Re-read the edited entity note and verify that it contains only identity facts plus lightweight links/pointers. Agents may leave behind summary lines that still include operational specifics like cadence, schedules, or checklist details. If that happens, run a tightening pass so those specifics live only in the canonical task/project/note that owns them.
* If a note becomes non-canonical during cleanup, default to converting it into an archived pointer note rather than deleting it. Keep it tiny: set status to archived, add one short handoff sentence pointing to the canonical note, trim related links to lightweight breadcrumbs, and preserve the changelog so the audit trail still makes sense. Delete only when the file is pure throwaway noise with no historical value.
* When consolidating “task confetti” into a project/notes-only structure, preserve the durable learning/context in the canonical project or note first, then remove operational task files and their crons. Read the relevant templates before editing, list live cron jobs, remove any cron IDs tied to the deleted tasks, update `user-context.md`, and search for old task slugs afterward. If a non-task note is merged into the project, prefer an archived pointer note for backlink/audit safety; if task notes are pure operational clutter and the user asked to remove tasks, hard-delete them after migrating content. In changelogs/provenance, mention old slugs as code/plain text rather than wikilinks so cleanup documentation does not recreate broken links.

- **Schema migrations must hit templates and live files.** If a frontmatter field is added, removed, renamed, or retyped, update every relevant `_template.md` and backfill all existing notes of that content type in the same pass. When the user asks for historical backfill, derive values from stable file metadata where possible (for example, use each file's modified time when introducing an `updated` field) instead of inventing timestamps.
- **Preserve provenance when backfilling from file metadata.** If the value you are backfilling comes from file metadata that your edit would overwrite — especially modified time — capture that metadata before writing, use it to populate the new field, and preserve or restore the original mtime afterward for the files where that timestamp is now the canonical historical value.
- **Do not leave fake wikilinks in prose while documenting cleanup.** If you are mentioning a removed, broken, or non-canonical note name in changelogs, reports, or `user-context.md`, write it as plain text or code (for example, `trialcheck`), not as `[[trialcheck]]`. The lint pass treats literal wikilink syntax anywhere in the vault as a real link target, so “documenting the broken link” can accidentally recreate the same broken-link flag.
- **When fixing broken wikilinks from a lint report, clean both the source and the report artifacts.** Start by searching the vault for the exact broken targets, decide whether each target should become a real note, an existing canonical wikilink, or plain text, then also scan `.agents-log/lint-reports/latest.md`, the timestamped report, and the relevant task changelog for the same `[[broken-target]]` strings. Convert report/changelog mentions to code/plain text so the documentation doesn't keep the broken link alive.
- **Verify wikilink cleanup with the shared lint script.** After edits, search for the exact `[[broken-target]]` pattern across both `~/my-data` and `.agents-log`, then run `python3 ~/.hermes/scripts/life-os/nightly-lint.py --dry-run`. Only report success when it returns `broken_wikilinks: 0` and `flags: 0`.
- **When the user corrects a canonical name or spelling, clean the hidden trails too.** Renaming the live note and updating active wikilinks is not enough. Also scan `user-context.md`, recent agent-written reports under `.agents-log/`, and other cleanup artifacts for the stale name/path so the old spelling does not keep resurfacing in search results or future lint narratives. If an audit/report needs to preserve the history, describe the old name in plain text or code rather than leaving it as a live-looking path or wikilink.

- **When sweeping mistaken task `due_date` values, separate true deadlines from reminder timing.** First make a backup archive of the vault. Then enumerate every task with a non-empty `due_date` alongside `status`, `recurrence`, `cron_id`, `next_reminder_time`, title, and nearby reasoning/body text. Remove `due_date` only when the date came from a requested reminder/action time or agent-inferred scheduling window, and preserve `cron_id`, `next_reminder_time`, and `last_5_reminder_times`. Keep `due_date` for real events/deadlines such as birthdays, appointments, explicit completion-by dates, and externally meaningful follow-up bounds. Add changelog entries to edited tasks, update `updated`, write an audit report under `.agents-log/`, and verify by re-listing remaining non-empty due dates before reporting back.
